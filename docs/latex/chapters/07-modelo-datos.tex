\subsection{Decisiones de diseño del modelo}
\begin{description}[style=nextline]
  \item[DM-01] El estado ocupada/libre de una celda se calcula a partir de las estadías abiertas; no se guarda, para evitar datos contradictorios.
  \item[DM-02] La novedad se vincula a la estadía (tabla asociativa); el vehículo se obtiene de ella sin redundancia.
  \item[DM-03] El vencimiento se identifica por el pago vencido. \texttt{numero\_envio} (1 = primero, 2 = reenvío) con unicidad por pago hace que la base de datos imponga RN-11 y RN-22. El proceso de retiro se calcula, por lo que RN-17 se cumple al pagar.
  \item[DM-04] Desnormalización controlada: el pago guarda una copia del valor, y el aviso guarda el destinatario, el asunto y el cuerpo, como evidencia histórica.
  \item[DM-05] Todas las claves foráneas usan \texttt{ON DELETE RESTRICT}; los registros se desactivan, nunca se borran (RN-07).
  \item[DM-06] Los valores se guardan en pesos enteros (\texttt{INTEGER}).
  \item[DM-07] Zona horaria \texttt{America/Bogota}; Django guarda las fechas en UTC.
\end{description}

\subsection{Dependencias funcionales}
\begin{itemize}
  \item \texttt{usuario.id} $\rightarrow$ username, rol, \ldots; \texttt{username} $\rightarrow$ id (clave candidata).
  \item \texttt{propietario.id} $\rightarrow$ nombre\_completo, numero\_documento, telefono, correo, direccion; \texttt{numero\_documento} $\rightarrow$ id.
  \item \texttt{vehiculo.id} $\rightarrow$ placa, tipo, marca, nombre, modelo, color, propietario\_id; \texttt{placa} $\rightarrow$ id. Marca, nombre y modelo no determinan otros atributos.
  \item \texttt{celda.id} $\rightarrow$ codigo, tipo; \texttt{codigo} $\rightarrow$ id.
  \item \texttt{pago.id} $\rightarrow$ vehiculo\_id, periodo\_inicio, periodo\_fin, valor, fecha\_pago, registrado\_por\_id.
  \item \texttt{estadia.id} $\rightarrow$ vehiculo\_id, celda\_id, fechas y usuarios.
  \item \texttt{avisocorreo.id} $\rightarrow$ \ldots; (\texttt{pago\_id}, \texttt{numero\_envio}) $\rightarrow$ id cuando el número no es nulo.
\end{itemize}

\subsection{Normalización}
\begin{description}[style=nextline]
  \item[1FN] Todos los atributos son atómicos. Los vehículos de una novedad se guardan en la tabla asociativa, no como lista.
  \item[2FN] Las tablas con clave simple cumplen trivialmente; la única clave compuesta (\texttt{novedadestadia}) no tiene atributos fuera de la clave.
  \item[3FN] Ningún atributo no clave depende de otro atributo no clave. El vehículo de una novedad no se repite (DM-02) y el estado de la celda no se guarda (DM-01).
  \item[Excepciones justificadas] Las copias históricas de DM-04 representan el valor en el momento del hecho y no dependen del valor actual de la tarifa o del propietario.
\end{description}

SQLite tiene tipado flexible: los tipos declarados documentan la intención y Django valida los valores antes de guardarlos. Las restricciones \texttt{CHECK}, \texttt{UNIQUE} y de clave foránea sí las aplica el motor.

\subsection{Integridad y validación}
Las fechas de registro las asigna la aplicación con el reloj del sistema, para poder simularlas en las pruebas. Las reglas que cruzan tablas (RN-03 vigencia, RN-08 compatibilidad de celda, RN-16 presencia y RN-22 confirmación) se validan en los servicios, dentro de transacciones.

El script se ejecutó en SQLite 3.50.4 con \texttt{docs/sql/validar\_ddl.py}: \textbf{42 comprobaciones, 42 aprobadas}. Entre ellas se verificó el rechazo de una segunda estadía abierta por vehículo o por celda, de placas con formato inválido, de un segundo reenvío del correo y del borrado de un vehículo con estadías; y la aceptación de salidas que cruzan la medianoche y de novedades con dos vehículos.
